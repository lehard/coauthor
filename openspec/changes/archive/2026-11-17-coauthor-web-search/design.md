# Design: поиск соавтора в интернете через Yandex Search API

## Context

Мотивация и рамки описаны в `proposal.md`, требования — в дельтах `specs/`.

Что есть сейчас:
- Список инструментов соавтора статический: `COAUTHOR_TOOLS` в `agno/agents/coauthor_tools.py` состоит из `READING_TOOLS` и меняющих инструментов с подтверждением. AgentOS 3.1.10 не принимает инструменты, созданные на каждый запуск. Отказы инструменты возвращают строкой «Отказ: …» через `_answer`, доступ к беседе проверяет `_draft(run_context, "read")`.
- Расход пишет post-hook `record_usage` (`agno/agents/coauthor_usage.py`). Он строит `RunUsage` из метрик моделей `RunOutput` и вызывает `billing.record_runs` одной транзакцией. Упавшие и отменённые запуски дописываются из сессии при следующем запуске (`_earlier_runs`).
- Биллинг: журнал `billing.usage_records` хранит одну строку на запуск и модель. Цены моделей лежат в `model_prices.toml`, строгий разбор в `plans.py`. Расход периода — сумма `cost_rub` (`usage.period_spend`), отчёт — `usage.report`. Без цены модели соавтора API не стартует: `billing.check_model_price` в `agents/coauthor.py`.
- Обязательные внешние сервисы проверяются при старте явно, например `scanner_address()` у ClamAV в `app/main.py`.
- `httpx` уже стоит как зависимость Agno. XML разбирается стандартной библиотекой.

## Goals / Non-Goals

**Goals:**
- Один читающий инструмент `web_search` с пределом вызовов на запуск, без состояния вне запуска.
- Учёт стоимости поисков в том же журнале и той же транзакции, что токены.
- Явные отказы на каждом шаге: настройки, HTTP, формат ответа, предел.

**Non-Goals:**
- Общий клиент внешних поисковиков и абстракция «провайдер поиска»: провайдер один.
- Асинхронный клиент: инструменты соавтора синхронные, как остальные инструменты ядра.

## Decisions

### 1. Клиент Яндекса — модуль `agno/agents/web_search.py`, инструмент — в `coauthor_tools.py`

В `web_search.py` лежат три вещи: чтение настроек, запрос к Yandex Search API, разбор XML в список результатов и текст для модели. Сам инструмент `web_search(run_context, query)` находится в `coauthor_tools.py` рядом с `search_sources`. Он проверяет беседу через `_draft(..., "read")`, проверяет предел, вызывает клиент и отдаёт текст через `_answer`.

Альтернативы:
- `agno/core/`. Ядро — домен произведения, внешнего поиска в нём нет, и ядро не зависит от внешних сервисов, кроме ClamAV для загрузок.
- `app/registry.py`. Это палитра Studio, у неё свой веб-инструмент Parallel.
- Toolkit Agno. Для Яндекса готового нет, а свой Toolkit не даёт ничего сверх функции в `READING_TOOLS`.

### 2. Запрос: Search API v2, синхронный, XML

Запрос — `POST https://searchapi.api.cloud.yandex.net/v2/web/search` с заголовком `Authorization: Api-Key <ключ>`. Тело:
- `query.searchType = SEARCH_TYPE_RU`, `query.queryText`;
- `region = "225"`, `l10n = LOCALIZATION_RU`, `folderId`;
- `groupSpec.groupsOnPage = 5`, `docsInGroup = 1`, `maxPassages = 5`;
- `responseFormat = FORMAT_XML`.

Ответ — JSON с `rawData`: в нём XML в Base64. Таймаут запроса 15 с. Ответ не 2xx, сетевая ошибка или таймаут дают `WebSearchFailed` с кодом ответа. Имена полей при реализации сверяются с документацией v2 (`api-ref/WebSearch/search`), на один запрос с настоящим ключом.

Ограничения Яндекса — до 400 знаков и 40 слов в запросе. Более длинный запрос получает отказ до обращения к Яндексу и не оплачивается.

Альтернатива — HTML-выдача. В ней есть реклама и колдунщики, разбирать её труднее.

### 3. Разбор XML: только ожидаемая структура, иначе отказ

Из `response/results/grouping/group/doc` берём `url`, `title` и `passages/passage`, а разметку `hlword` сводим к тексту через `itertext()`.

Элемент `response/error` с кодом 15 («ничего не нашлось») считается пустой выдачей: она оплачивается, и модель получает «ничего не нашлось». Это поведение проверяется при реализации на настоящем ответе. Любой другой код ошибки и ответ без `results` и без `error` дают `WebSearchFailed`.

Текст для модели состоит из строки «Найдено в интернете по запросу «…»:», затем для каждого результата номер, заголовок, адрес и отрывки, а в конце просьба давать автору ссылки. Для пустой выдачи — «В интернете ничего не нашлось по запросу «…»».

Обе формулировки — константы модуля. По ним `coauthor_usage` отличает оплачиваемый вызов (решение 5).

### 4. Предел 2 поиска на запуск — подсчёт по сообщениям запуска

`RunContext.messages` в Agno 3.1.10 — живой список сообщений текущего запуска. Сообщения истории в нём помечены `from_history=True`. Инструмент считает вызовы `web_search` в `tool_calls` сообщений ассистента без `from_history`. Текущий вызов уже есть в списке, поэтому если вызовов больше 2, инструмент возвращает отказ без запроса. Так же считаются параллельные вызовы в одном сообщении. Состояния вне запуска нет.

Если `messages` пуст или `None`, это ошибка: работы без предела не будет.

Альтернативы:
- `Agent.tool_call_limit` ограничивает все инструменты сразу.
- `session_state` пишется в данные Agno, и его пришлось бы сбрасывать между запусками.
- Словарь в памяти процесса растёт и теряется при перезапуске.

### 5. Оплачиваемые вызовы — по результатам в `RunOutput.tools`

`run_usage` в `coauthor_usage.py` дополнительно считает `ToolExecution` с `tool_name == "web_search"`, у которых `result` начинается с одной из двух констант выдачи (решение 3). Отказы — предел, пустой или длинный запрос, сбой, чужая беседа — начинаются с «Отказ:» и не оплачиваются. Так считается и запуск после паузы подтверждения, и упавший запуск из сессии, потому что `_earlier_runs` вызывает тот же `run_usage`.

Альтернатива — писать расход прямо из инструмента. Тогда появляется вторая точка записи вне транзакции запуска и теряется повтор для упавших запусков.

### 6. Биллинг: цены инструментов в том же файле, новая таблица

- В `model_prices.toml` добавляется обязательная таблица `[tools]`: `[tools.web_search] call_rub = 0.488`, с комментарием об источнике цены. `parse_prices` требует `models` и `tools`, а неизвестные поля отклоняет. `Prices` получает `by_tool` и `tool(name)` с ошибкой `UnknownTool`.
- Интерфейс `billing/__init__.py` получает `check_tool_price(tool)`. `agents/coauthor.py` вызывает его для `web_search` при старте рядом с `check_model_price`.
- `RunUsage` получает `tools: tuple[ToolUsage, ...]` (`tool`, `calls`), без вызовов — пустой кортеж. `record_run` в той же транзакции вставляет строки `tool_usage_records`, повтор пропускает через `on_conflict_do_nothing(run_id, tool)`.
- `period_spend` и `report` суммируют `cost_rub` обеих таблиц в периоде. `ReportRow` получает `paid_tool_calls`, а `python -m admin report` выводит столбец «поиски».
- Миграция `b0002_tool_usage_records` пишется вручную под `billing/tables.py`.

Альтернатива — столбцы поисков в `usage_records`. Там одна строка на модель, и поиски пришлось бы приписывать одной из моделей запуска.

### 7. Настройки и старт

`web_search.settings()` читает `YANDEX_SEARCH_API_KEY` и `YANDEX_CLOUD_FOLDER_ID`. Если переменная пуста, бросается `RuntimeError` с её именем. Вызов стоит в `agents/coauthor.py` при импорте, как проверки биллинга, поэтому без настроек не стартует ни API, ни `python -m evals`.

Переменные идут в блок Required файла `example.env`. Как контейнер API получает `.env`, при реализации сверяется с `compose.yaml` и `compose.prod.yaml`, по аналогии с `CLAMAV_HOST`.

### 8. Логи без запроса и ключа

При сбое пишется `log.error` с кодом HTTP или кодом ошибки Яндекса и типом исключения. Текста запроса и заголовков в логе нет. В спанах Phoenix аргументы инструментов не пишутся, это уже так по спеке `agent-tracing`.

### 9a. Не чаще одного запроса в секунду (владелец, 2026-11-17)

Квота Yandex Search API по умолчанию — 1 синхронный запрос в секунду. На стенде второй поиск того же ответа ушёл
меньше чем через секунду и получил `HTTP 429`. Поэтому в `web_search.py` стоит одна блокировка на процесс и время
прошлого запроса. Следующий запрос ждёт, пока с прошлого не пройдёт секунда, и только потом уходит. Запросы идут
по одному, в том числе от разных авторов; задержка до секунды на каждого ждущего. API у нас один экземпляр, поэтому
блокировки на процесс хватает.

Это соблюдение квоты, а не повтор: `429` по-прежнему даёт явный отказ без второго запроса.

Альтернативы:
- Поднять квоту у Яндекса. Это действие владельца, и при одновременных авторах оно отказ не исключает.
- Повтор после `429`. Это была бы маскировка сбоя, она запрещена.

### 9. Промпт

В `SKILL.md` меняется раздел «Факты реального мира»: когда искать, как писать запрос, ссылки, поведение при отказе. В раздел «Задание на исследование» добавляется строка, что поиск его не подменяет. В справку «О сервисе «Соавтор»» добавляется строка о поиске и лимите. Короткое описание инструмента в docstring задаёт его назначение для модели.

## Risks / Trade-offs

- [Формат v2 или XML отличается от ожидаемого] → разбор пишется по сохранённому настоящему ответу (образец в `agno/tests/data/`), при неизвестной структуре инструмент явно отказывает.
- [Подсчёт оплачиваемых вызовов завязан на начало текста результата] → константы лежат в одном модуле и импортируются, а тест проверяет, что оба вида выдачи оплачиваются и отказ не оплачивается.
- [Квота 1 запрос в секунду] → при параллельных авторах Яндекс отвечает ошибкой, и автор видит отказ. Квоту поднимают через поддержку, если это станет заметно.
- [Модель вставляет в запрос куски сюжета] → это правило промпта и ничем не гарантируется. Проверяется глазами на стенде.
- [API не стартует без новых переменных] → переменные кладутся на сервер до выпуска релиза (план ниже).

## Migration Plan

1. Владелец создаёт в Yandex Cloud платёжный аккаунт, каталог и сервисный аккаунт с ролью `search-api.webSearch.user`, выпускает API-ключ.
2. Ключ и id каталога кладутся в `.env` основной папки (локальный стенд) и до релиза — в `/etc/authorled/authorled.env` на сервере. Изменение на сервере только с подтверждения владельца.
3. Релиз применяет миграцию `b0002` шагом `agentos-migrate`.
4. Откат: прошлый релиз работает и с новой таблицей, потому что миграция только добавляет таблицу. Переменные Яндекса прошлый релиз не читает.
