## MODIFIED Requirements

### Requirement: Интерфейс биллинга
Публичный интерфейс биллинга MUST давать операции: выдать подписку при входе, проверить лимит, дать место для файлов по тарифу, записать расход запусков (токены по моделям и оплачиваемые вызовы платных инструментов), проверить цену платного инструмента, найти беседу запуска пользователя, построить отчёт по расходу и сменить тариф. Операции MUST принимать и возвращать простые значения (идентификаторы, числа, строки, время, неизменяемые записи) и MUST NOT принимать соединение с базой. Каждая операция MUST выполняться в своей транзакции: при ошибке её изменения MUST NOT сохраняться.

#### Scenario: Ошибка посреди записи расхода
- GIVEN запись расхода двух запусков, второй из которых нарушает ограничение журнала
- WHEN вызывается операция записи расхода
- THEN операция MUST завершиться ошибкой
- AND в журнале MUST NOT появиться строки ни одного из двух запусков

#### Scenario: Пользователь в отчёте по идентификатору
- GIVEN у пользователя есть подписка и расход
- WHEN вызывается операция отчёта
- THEN строка отчёта MUST называть пользователя его идентификатором ядра и MUST NOT содержать почты

#### Scenario: Беседа чужого запуска
- GIVEN в журнале есть запуск `r1` пользователя А
- WHEN беседу запуска `r1` ищут для пользователя Б
- THEN операция MUST завершиться отказом «запуск не найден», как для несуществующего запуска

#### Scenario: Место по идентификатору
- GIVEN у пользователя действующая подписка
- WHEN вызывается операция места для файлов с его идентификатором ядра и временем
- THEN операция MUST вернуть число байт и MUST NOT обращаться к схеме ядра

#### Scenario: Расход запуска с поисками одной транзакцией
- GIVEN запуск с токенами модели и двумя оплачиваемыми поисками, а строка вызовов нарушает ограничение журнала вызовов
- WHEN вызывается операция записи расхода
- THEN операция MUST завершиться ошибкой
- AND в журнале расхода MUST NOT появиться строки этого запуска

## ADDED Requirements

### Requirement: Таблица журнала вызовов инструментов биллинга
Схема `billing` MUST содержать таблицу `tool_usage_records`, одна строка на запуск и платный инструмент, с теми же связями, что у `usage_records`: пользователь ядра по значению, подписка внешним ключом с запретом удаления. Пара `run_id`, `tool` MUST быть уникальной, число вызовов `calls` — больше нуля, стоимость — неотрицательной.

#### Scenario: Столбцы
- GIVEN все миграции применены
- WHEN перечисляются столбцы `billing.tool_usage_records`
- THEN они MUST быть такими: `id` (`uuid`, первичный ключ); `user_id` (обязательный `uuid`); `subscription_id` (ссылка на `billing.subscriptions.id`); `run_id`, `session_id`, `agent_id`, `tool` (непустой текст); `run_status` (`completed`, `error` или `cancelled`); `calls` (целое); `cost_rub` (шесть знаков); `occurred_at`, `created_at`

#### Scenario: Повтор вызовов запуска
- GIVEN в журнале вызовов есть строка запуска `r1` инструмента `web_search`
- WHEN вставляется вторая строка `r1` и `web_search`
- THEN база MUST отклонить вставку

#### Scenario: Ноль вызовов
- GIVEN подписка пользователя
- WHEN вставляется строка журнала вызовов с `calls` = 0
- THEN база MUST отклонить вставку

#### Scenario: Подписка с вызовами
- GIVEN у подписки есть строки журнала вызовов
- WHEN подписка удаляется
- THEN база MUST отклонить удаление
