## MODIFIED Requirements

### Requirement: Цены моделей как данные
Цена псевдонима модели LiteLLM MUST задаваться файлом данных биллинга: рубли за миллион токенов входа, входа из кэша и выхода, все неотрицательные и обязательные. Если у модели соавтора нет цены, API MUST NOT стартовать, а ошибка MUST называть модель. Стоимость запуска MUST считаться так: (вход − вход из кэша) × цена входа + вход из кэша × цена кэша + выход × цена выхода, делённое на миллион; токены входа включают токены из кэша. Стоимость LiteLLM в долларах MUST храниться только для сверки и MUST NOT влиять на расход. В том же файле MUST задаваться цена платного инструмента соавтора — рубли за вызов, неотрицательная и обязательная; другие поля MUST отклоняться. Цена поиска в интернете `web_search` — 0,488 ₽ за вызов в любое время суток. Если у платного инструмента соавтора нет цены, API MUST NOT стартовать, а ошибка MUST называть инструмент.

#### Scenario: Расчёт стоимости
- GIVEN цена модели 30 ₽ вход, 0,6 ₽ кэш, 120 ₽ выход за миллион
- WHEN запуск потратил 10 000 токенов входа, из них 4 000 из кэша, и 2 000 токенов выхода
- THEN стоимость MUST быть 0,4224 ₽

#### Scenario: Модели нет в файле цен
- GIVEN у модели соавтора нет строки в файле цен
- WHEN API стартует
- THEN старт MUST завершиться ошибкой, называющей эту модель

#### Scenario: Стоимость поисков
- GIVEN цена `web_search` 0,488 ₽ за вызов
- WHEN запуск соавтора дважды получил выдачу поиска в интернете
- THEN стоимость поисков запуска MUST быть 0,976 ₽ и MUST прибавляться к стоимости токенов

#### Scenario: Нет цены поиска
- GIVEN в файле цен нет цены `web_search`
- WHEN API стартует
- THEN старт MUST завершиться ошибкой, называющей `web_search`

### Requirement: Журнал расхода соавтора
После каждого запуска соавтора биллинг MUST записывать в журнал по каждой модели запуска: пользователя, подписку, запуск, беседу, агента, модель, статус запуска, токены входа, входа из кэша и выхода, стоимость в рублях, стоимость LiteLLM в долларах (если есть) и время начала запуска. Повторная запись того же запуска и модели MUST NOT создавать вторую строку. По каждому платному инструменту запуска биллинг MUST записывать в журнал вызовов инструментов пользователя, подписку, запуск, беседу, агента, инструмент, статус запуска, число оплачиваемых вызовов, стоимость в рублях и время начала запуска; повтор того же запуска и инструмента MUST NOT создавать вторую строку. Оплачивается вызов поиска, который вернул выдачу, в том числе пустую; отказ до запроса и сбой поиска MUST NOT оплачиваться. Расход периода MUST быть суммой стоимости токенов и платных вызовов. Упавшие и отменённые запуски беседы, у которых есть токены, MUST дописываться в журнал при следующем запуске той же беседы. Завершённый запуск без токенов модели MUST давать явную ошибку записи. В журнале MUST NOT быть текста произведений и почты.

#### Scenario: Одна запись на запуск
- GIVEN автор отправил соавтору сообщение, и запуск завершился
- WHEN post-hook записывает запуск второй раз
- THEN в журнале MUST быть ровно одна строка этого запуска с токенами и стоимостью в рублях

#### Scenario: Отменённый запуск
- GIVEN автор остановил ответ после вызова модели, и запуск сохранён отменённым с токенами
- WHEN автор пишет в ту же беседу снова
- THEN отменённый запуск MUST появиться в журнале со статусом `cancelled` до проверки лимита

#### Scenario: Запуск с поисками
- GIVEN запуск соавтора дважды получил выдачу поиска в интернете и один раз получил отказ о пределе поисков
- WHEN post-hook записывает запуск
- THEN в журнале вызовов MUST быть одна строка этого запуска и `web_search` с 2 вызовами и стоимостью 0,976 ₽
- AND расход периода MUST вырасти на стоимость токенов и 0,976 ₽

#### Scenario: Сбой поиска не оплачивается
- GIVEN в запуске единственный поиск в интернете вернул отказ о сбое Яндекса
- WHEN post-hook записывает запуск
- THEN строки журнала вызовов этого запуска MUST NOT быть

#### Scenario: Упавший запуск с поиском
- GIVEN запуск упал после выдачи поиска, и в нём есть токены
- WHEN автор пишет в ту же беседу снова
- THEN запуск MUST появиться и в журнале расхода, и в журнале вызовов со статусом `error` до проверки лимита

### Requirement: Команды администратора
Скрипт администратора MUST требовать цель (`local` или `prod`) и выполнять команды в контейнере API через операции биллинга, а почты MUST брать у ядра:
- `report` — по каждому неудалённому пользователю почта, тариф, начало и конец текущего периода, число запусков, токены (вход, кэш, выход), число оплаченных поисков в интернете, расход в рублях (токены и поиски), лимит, остаток и сумма LiteLLM в долларах за период;
- `set-plan <почта> <тариф>` — смена тарифа пользователя с этой почтой.
Если неудалённых пользователей с почтой нет или их больше одного, `set-plan` MUST завершаться ошибкой и ничего не менять. Других ручных настроек лимита MUST NOT быть.

#### Scenario: Отчёт
- GIVEN у пользователя за период два запуска соавтора
- WHEN администратор выполняет `report`
- THEN строка пользователя MUST показывать его почту, 2 запуска, сумму их токенов и расход, а остаток MUST быть лимитом минус расход

#### Scenario: Отчёт с поисками
- GIVEN у пользователя за период один запуск соавтора с двумя оплаченными поисками
- WHEN администратор выполняет `report`
- THEN строка пользователя MUST показывать 2 поиска, а расход MUST включать их стоимость

#### Scenario: Неизвестная почта
- GIVEN нет пользователя с почтой `nobody@example.com`
- WHEN администратор выполняет `set-plan nobody@example.com beta`
- THEN команда MUST завершиться ненулевым кодом с сообщением о почте

#### Scenario: Удалённый пользователь не в отчёте
- GIVEN аккаунт пользователя удалён (`deleted_at` заполнено), а его подписка и журнал остались в биллинге
- WHEN администратор выполняет `report`
- THEN строки этого пользователя в отчёте MUST NOT быть
